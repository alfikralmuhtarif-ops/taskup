# TaskUp — Security Status

**Last updated:** August 30, 2026

This is a factual status report of what's actually implemented in the codebase today, what still needs manual action in a provider console before launch, and what open gaps exist. It's written to be read alongside [`PRIVACY_POLICY.md`](./PRIVACY_POLICY.md) and [`TERMS_OF_SERVICE.md`](./TERMS_OF_SERVICE.md), which reference several of the same gaps.

**Context that shapes everything below:** TaskUp is currently a local development project. There is no git repository, no CI/CD, no chosen hosting provider, and no third-party service (SMS, push, object storage, AI) actually wired up — all of those run as local dev-stub adapters behind interfaces (`ISmsSender`, `IPushSender`, `IFileStorage`, `IAiTaskInsightProvider`), ready to be swapped for real implementations without touching calling code.

---

## 1. Transport encryption (TLS)

| Item | Status |
|---|---|
| HTTP → HTTPS redirect | ✅ Implemented (`UseHttpsRedirection()`, `Program.cs`) |
| HSTS (`max-age=31536000`, `includeSubDomains`) | ✅ Implemented, active outside Development |
| HSTS `preload` | ⏸ Deliberately not enabled — submission to hstspreload.org is manual, one-way, and should only happen once every subdomain is confirmed HTTPS-only in production |
| Security headers (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Content-Security-Policy`) | ✅ Implemented on the API (`Program.cs` middleware). `default-src 'none'` is safe here because this API only ever returns JSON |
| Kestrel minimum TLS version | ✅ Configured to TLS 1.2/1.3 only |
| Cookie flags (`Secure`/`HttpOnly`/`SameSite`) | N/A today — the app sets no cookies anywhere (pure JWT bearer + refresh token in the JSON body). If a cookie is ever introduced, it must get all three flags |
| Mobile ATS (iOS) / Network Security Config (Android) | N/A — no native iOS/Android app project exists yet. The current "mobile app" is a React web prototype opened in a browser (including inside the iOS Simulator), not a native binary. Revisit this the moment a native or Capacitor-style wrapper ships |
| **Manual action needed:** provider-level TLS/HSTS | ⚠️ Whichever reverse proxy/load balancer terminates TLS in front of the API (ALB, nginx, Cloudflare, etc.) must independently be configured with the same minimum TLS version and HSTS policy — Kestrel's settings only apply if Kestrel itself terminates TLS directly |
| **Manual action needed:** DB connection TLS | ⚠️ The production Postgres connection string must add `SSL Mode=Require` (or `VerifyFull` with the provider's CA bundle). The current local dev connection string is plaintext-loopback, which is fine only because it never leaves `localhost` |

## 2. At-rest encryption

| Item | Status |
|---|---|
| `User.Phone` — AES-256-GCM field encryption | ✅ Implemented (transparent EF Core `ValueConverter`, see `TaskUpDbContext.OnModelCreating`) |
| `Message.Text` — AES-256-GCM field encryption | ✅ Implemented, same mechanism |
| `Note.Title` / `Note.Content` — AES-256-GCM field encryption | ✅ Implemented, same mechanism. `Content`'s DB column is named `ContentEncrypted` to make ciphertext-at-rest visually obvious in `psql`. Search over these fields decrypts and filters in memory per-user rather than pushing `ILIKE` to SQL (see §3 below for why) |
| `User.PhoneHash` — deterministic lookup column | ✅ Implemented. **Deliberately unkeyed SHA-256**, not HMAC — the contact-sync feature (D8) requires the client to independently reproduce the same hash from a normalized phone number with no shared secret, which rules out a keyed hash for this column |
| Search/lookup impact of the above | ⚠️ **Product tradeoff, made with sign-off:** phone number search (People search, admin user search) is now exact-match only — partial/substring phone search no longer works. "Search inside message content" was removed entirely from the Conversations search scope, which now matches by the other participant's name instead. Name-based search is unaffected everywhere |
| `Invite.Phone`, `OtpRequest.Phone` | Left **unencrypted by design** — both are short-lived/ephemeral (an OTP request expires in minutes; an invite is a transient pointer, not the durable profile record), unlike `User.Phone`. A follow-up could extend the same pattern to them if wanted |
| Key rotation | ✅ Mechanism implemented: `EncryptionOptions.Keys` is a version→key dictionary, `CurrentKeyVersion` controls what new writes use, and every ciphertext is prefixed with its key version (`v1:...`) so old and new keys can coexist. **Rotation runbook:** (1) add the new key as a new version in config, (2) deploy, (3) new writes now use it automatically, (4) run a background job that re-reads and re-writes old rows (forces re-encryption under the new key), (5) once confirmed migrated, retire the old key from config |
| Password hashing | N/A — TaskUp has no passwords anywhere; auth is phone+OTP only |
| OTP code / refresh token hashing | ✅ SHA-256 (`SecurityTokenHelpers.Hash`) — appropriate here because these are high-entropy, rate-limited (5 attempts), short-lived (OTP: 5 min) or revocable (refresh token) values, not password material. Argon2id/bcrypt is the right tool for low-entropy human-chosen passwords, which don't exist in this app |
| Log content | ✅ `LoggingSmsSender`/`LoggingPushSender` now only log full detail (OTP code, phone, notification body) in `Development`; other environments log masked/shape-only info. EF Core's own SQL logs already redact parameter values by default (`EnableSensitiveDataLogging` is not enabled anywhere in the codebase) |
| Secrets in source control | ✅ `backend/.gitignore` added (there was none before). ⚠️ There is currently no git repository at all in this project — harmless today, but `Jwt:SigningKey`, `AdminBootstrap:Secret`, and `Encryption:Keys` must move from `appsettings.json` into environment variables/a secrets manager **before** the first `git init` and **before** any real deployment |
| **Manual action needed:** provider-level disk/DB/backup encryption | ⚠️ No hosting provider is chosen yet. Checklist per realistic candidate: |

**AWS** — enable RDS storage encryption at creation time (can't be turned on after the fact without a snapshot-restore), enable EBS volume encryption, enable S3 default bucket encryption (SSE-S3 or SSE-KMS) for any object storage, and confirm automated RDS backups inherit encryption (they do, automatically, if the source DB is encrypted).

**Supabase** — Supabase encrypts data at rest by default on its managed Postgres; confirm this is still current in their docs at deployment time, and enable Storage bucket encryption if using Supabase Storage.

**Self-managed VPS** (DigitalOcean/Hetzner/etc.) — enable full-disk encryption (LUKS) on the volume hosting the Postgres data directory *before* first writing data (LUKS can't be applied retroactively to an existing unencrypted volume without a rebuild), and make sure any backup destination (off-box snapshots, `pg_dump` archives) is encrypted too, not just the live disk.

## 3. Resolved this pass

| Item | What was built |
|---|---|
| Self-service account deletion | `DELETE /users/me` (`IdentityService.DeleteAccountAsync`) anonymizes `Name`/`AvatarUrl`/`Phone`, sets `IsDisabled` + `DeletedAt`, and revokes every active session. Referential integrity (FK-Restrict throughout the schema) means this can't be a hard delete without breaking other users' tasks/messages — see the code comment on `User.DeletedAt`. Reachable in the mobile prototype from Profile → Delete Account |
| Report/block-user feature | `UserBlock`/`UserReport` entities, `/people/{id}/block`, `/people/{id}/report`, `/people/blocked`. `ChatService` rejects new conversations/messages between blocked pairs in either direction (`EnsureNotBlockedAsync`). Admin review via `/admin/reports` and the admin panel's new "البلاغات" page. Reachable in the mobile prototype's chat header "⋮" menu |
| Admin content-access audit log | `AdminAccessLog` — written by `AdminService.GetUserAsync`/`GetTaskAsync`/`GetProjectAsync` (content views, not list views) via `LogAccessAsync`. Viewable via `/admin/audit-log` and the admin panel's new "سجل التدقيق" page |
| Notes feature — encrypted, taggable, soft-deletable personal notes, optionally linked to a task | Requested by the user, with three mandatory security requirements: field encryption, ownership checks on every operation, and Postgres Row-Level Security. New `Note`/`Tag`/`NoteTag` entities (`TaskUp.Domain/Notes/`); `Title`/`Content` AES-256-GCM encrypted (see §2 row above); ownership enforced in C# by `NoteAuthorizationService` (every read/update/delete checks `Note.UserId == callerId`, same pattern as `TaskAuthorizationService` but simpler since a note has exactly one owner). **Row-Level Security**: migration `AddNotesFeature` runs `ALTER TABLE "Notes"/"Tags"/"NoteTags" ENABLE/FORCE ROW LEVEL SECURITY` plus per-table policies keyed on a `app.current_user_id` Postgres session variable (`NoteTags`' policy checks ownership via an `EXISTS` back to `Notes`); a new `NoteRlsActionFilter`, scoped only to `NotesController` via `[ServiceFilter]`, wraps each request in an explicit transaction and sets that session variable — this is the first use of Postgres RLS anywhere in this codebase, deliberately scoped narrowly so it doesn't add transaction-per-request behavior to Tasks/Projects/Chat/etc. **Honest caveat, verified live**: the app's Postgres role (`taskup`) owns these tables, and Postgres RLS — even with `FORCE` — never restricts the table owner. Confirmed via `psql`: as the `taskup` role, `SET app.current_user_id` to a wrong user still returned the row (RLS is a no-op for the owner); as a freshly-created **non-owner** role granted only `SELECT`, the same test correctly returned 0 rows for a wrong user and 1 for the right one (the policy itself is correct and would fully enforce isolation once the app connects as a non-owner role — deferred alongside the existing "hosting provider TBD" item, not a new gap). So today RLS is real, tested, and enforced against any *other* role, while the C# ownership checks above remain the actual enforced boundary for the app's own connection. **Search**: content is encrypted, so `ILIKE` can't run server-side against it — chose decrypt-and-filter-in-memory per user (bounded working set) over a blind-index/HMAC token table, matching the same tradeoff already made for `User.Phone`/`Message.Text` search elsewhere in this codebase (see §2). **Trash**: soft delete (`Note.DeletedAt`) + `NotesTrashPurgeJob` (mirrors `OverdueTaskSweepJob`'s `BackgroundService` shape) hard-deletes anything past 30 days in Trash, every few hours. No note content is ever logged anywhere in the new code. Verified live end-to-end (create/autosave/search/pin/tag/delete/restore, plus the RLS `psql` tests above) |
